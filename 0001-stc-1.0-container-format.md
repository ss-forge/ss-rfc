## 1. Summary

This specification defines the Sovereign Tensor Container (STC-1.0) format—a hermetic, single-file binary container designed for zero-copy Unified Direct Memory Access (DMA) execution, embedded lexical tokenization, and cryptographic provenance attestation. 

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED",  "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119.

---

## 2. Motivation & Structural Architecture

Existing neural network storage formats require runtimes to parse disparate files, perform CPU re-alignment of tensor weight buffers, and load external tokenizers before execution. STC-1.0 eliminates these inefficiencies by strictly organizing data into seven tiers across three macro-regions.

```text
+------------------------------------------------------------------------------+
| 📦 STC-1.0 SEVEN-TIER CONTAINER ARCHITECTURE MATRIX                          |
+--------+------------+--------------------------------------------------------+
| REGION | TIER BLOCK | DESCRIPTIVE ROLE & CONTENTS                            |
+--------+------------+--------------------------------------------------------+
| HEADER | HEADER     | Magic Bytes (STC1) + Protocol Version + Metadata       |
|        | TRUST      | C2PA Provenance Signature + SHA-256 Payload Hash       |
|        | LEXCON     | Lexical Cipher (Vocab, BPE Merges, Regex, Templates)   |
+--------+------------+--------------------------------------------------------+
| BODY   | AXIS       | Memory Strides + Quantization Type + Dimensional Layout|
|        | MAP        | Semantic Layer Roles (Attention, MoE, MLP)             |
|        | TENSOR     | 64-Byte Aligned Contiguous mmap-Ready Weight Buffer    |
+--------+------------+--------------------------------------------------------+
| FOOTER | PROV       | Optional Trailing Data Lineage & Audit Footer (EOF)    |
+------------------------------------------------------------------------------+
```

## 3. Macro-Region & Block Specifications

### 3.1 Header Region (Metadata & Security)

The Header Region occupies the initial bytes of the container. 

1. **HEADER Block (Envelope Initialization):**
   - **Magic Identifier (4 bytes):** The ASCII string `STC` followed by `0x01` (`[0x53, 0x54, 0x43, 0x01]`).
   - **Protocol Version (4 bytes):** A 32-bit unsigned little-endian integer. Implementations MUST support version `1`.
   - **Metadata Length (4 bytes):** A 32-bit unsigned little-endian integer specifying the byte length of the subsequent metadata payload.
   - **Metadata Payload:** A JSON-encoded string containing architectural classification, context window length, parameter count, and multi-shard geometry (e.g., shard count, shard byte size).

2. **TRUST Block (Cryptographic Attestation):**
   - A length-prefixed binary block containing a C2PA standard manifest, root payload SHA-256 hashes, and SPDX license strings. 
   - Modifications to the TENSOR block MUST invalidate this cryptographic signature.

3. **LEXCON Block (Lexical Substrate):**
   - Embeds the lexical substrate. Fields include:
     - `Algorithm`: An 8-bit unsigned integer (0 = BPE, 1 = Unigram, 2 = WordPiece).
     - `Vocab Table`: A contiguous buffer of null-terminated UTF-8 strings.
     - `Merge Ranks`: An array of 32-bit unsigned integer pairs representing BPE merge rules.
     - `Special Tokens`: Standardized 32-bit unsigned integers mapped to BOS, EOS, PAD, and EOT token IDs.
     - `Templates`: Length-prefixed UTF-8 strings for pre-tokenization regex and chat formatting.

### 3.2 Body Region (Hardware & Tensor Payload)

4. **AXIS & MAP Blocks:**
   - Encoded as a serialized JSON or FlatBuffer index mapping logical network identifiers (e.g., `model.embed_tokens.weight`) to physical tensor payload bounds.
   - Each entry MUST specify: 
     - `name`: UTF-8 string identifier.
     - `shape`: Array of 64-bit unsigned integers.
     - `quantization`: String identifier (e.g., `"f32"`, `"fp8_e4m3"`, `"q4_k"`, `"iq3_s"`).
     - `byte_offset`: 64-bit unsigned integer relative to the start of the TENSOR block.
     - `byte_length`: 64-bit unsigned integer.

5. **TENSOR Block:**
   - A flat, unencoded binary buffer containing raw model weights designed for zero-copy memory mapping.

### 3.3 Footer Region (Trailing Lineage)

6. **PROV Block (Optional Lineage Footer):**
   - Located exactly at the tail of the file.
   - **Payload Size (8 bytes):** A 64-bit unsigned little-endian integer detailing the metadata byte length.
   - **Magic Sentinel (4 bytes):** The ASCII string `STCP` (`[0x53, 0x54, 0x43, 0x50]`).
   - Contains a JSON-encoded payload with SHA-256 dataset hashes, pipeline identifiers, synthetic data ratios (32-bit float), and a boolean PII scrub flag.

#### Trailing Footer Parsing Sequence:
Parsers MUST seek to `EOF - 4 bytes` and inspect for the `STCP` sentinel. If present, parsers seek backward by `Payload Size` bytes to read the lineage metadata. If absent, the container MUST be processed without trailing lineage.

## 4. Memory Boundary Alignment Rule

To achieve zero-copy memory mapping on modern unified memory architectures, CPU re-alignment of tensor memory MUST be avoided.

All metadata blocks from `HEADER` through `MAP` MUST be padded with null bytes (`0x00`) to 64-byte physical boundaries according to the following formula:

$$\text{padding\_bytes} = (64 - (\text{unpadded\_length} \pmod{64})) \pmod{64}$$

Enforcing this rule mathematically guarantees that the `TENSOR` weight buffer begins exactly on a 64-byte physical cache line boundary.

---

## 5. Security & Validation Rules

Runtimes MUST enforce the following validation steps before allocating execution buffers:
1. **Magic Marker Validation:** The parser MUST inspect the first 4 bytes. If they do not match `[0x53, 0x54, 0x43, 0x01]`, execution MUST halt.
2. **Provenance Attestation:** The engine MUST compute the SHA-256 hash of the TENSOR block. If it fails to match the hash secured within the TRUST block, execution MUST halt.
