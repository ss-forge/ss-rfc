# RFC-0003: Sovereign Tensor Provenance (STP-1.0) & C2PA Verification

## 1. Summary

This specification defines the Sovereign Tensor Provenance (STP-1.0) standard—a cryptographic trust protocol and metadata vocabulary designed to bring verifiable supply-chain security to AI model distribution. It adapts the C2PA (Coalition for Content Provenance and Authenticity) standard into a specialized "AI Profile" for the Sovereign Tensor Container (STC-1.0).

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119.

---

## 2. Motivation & Scope

While the STC-1.0 specification (RFC-0001) dictates *where* provenance data is stored, STP-1.0 defines *how* that data is structured and cryptographically verified. Traditional neural network distribution relies on fragile, out-of-band checksums (e.g., external `.sha256` files) or blind trust. This leaves multi-gigabyte tensor payloads vulnerable to weight poisoning, unauthorized fine-tuning, and license stripping.

STP-1.0 resolves this by embedding a cryptographically signed C2PA manifest directly into the container's `TRUST` block, permanently binding the model's physical weights, creator identity, licensing, and training data lineage into a single, immutable, and auditable envelope.

---

## 3. The C2PA AI Profile (TRUST Block Schema)

The `TRUST` block MUST encapsulate a C2PA-compliant manifest encoded in CBOR (Concise Binary Object Representation) or JSON. This manifest acts as the primary cryptographic anchor for the container.

### 3.1 Mandatory Assertions
A compliant STP-1.0 manifest MUST contain the following embedded assertions:
- **Payload Hash Binding:** The absolute SHA-256 hash of the unpadded `TENSOR` block payload.
- **Developer Identity:** An X.509 digital certificate validating the identity of the model publisher or curation engine.
- **License Binding:** A valid SPDX License Identifier (e.g., `Apache-2.0`, `MIT`, `CC-BY-4.0`) dictating the permissible use of the weights.
- **Timestamping:** A secure, cryptographically signed timestamp recording the exact moment of container transpilation.

---

## 4. Cryptographic Verification Sequence

Compliant Sovereign Inference Engines (SIE-1.0) MUST execute the following verification sequence prior to mapping the `TENSOR` payload into execution memory:

1. **Manifest Extraction:** The engine extracts the C2PA manifest from the `TRUST` block.
2. **Signature Validation:** The engine cryptographically verifies the manifest signature against the embedded X.509 certificate chain.
3. **Payload Hashing:** The engine computes a runtime SHA-256 hash of the `TENSOR` block boundaries (as defined in the `MAP` block).
4. **Binding Comparison:** The engine compares the runtime hash against the immutable hash asserted in the C2PA manifest. 
5. **Execution Gate:** If the hashes match and the certificate is valid, the engine proceeds to zero-copy memory mapping. If any validation step fails, the engine MUST halt and refuse execution.

---

## 5. Data Lineage Vocabulary (PROV Block)

While the `TRUST` block protects the compiled container, the trailing `PROV` block standardizes the taxonomy for the model's historical training lineage. This enables independent compliance auditing.

If a `PROV` block is present, it MUST adhere to the following JSON schema definitions:

- `dataset_hashes` (Array of Strings): A list of SHA-256 hashes representing the exact training corpora used during the pre-training or fine-tuning phases.
- `pipeline_id` (String): The universally unique identifier (UUID) or semantic version of the data curation engine that generated the weights.
- `synthetic_ratio` (Float32): A numeric value between `0.0` and `100.0` explicitly declaring the percentage of synthetically generated tokens within the training mix.
- `pii_scrubbed` (Boolean): A strict `true` or `false` flag verifying whether the training data successfully passed automated Personally Identifiable Information (PII) removal filters.

---

## 6. Revocation & Poisoning Defense

To ensure long-term ecosystem security, STP-1.0 runtimes MUST adhere to strict defensive posturing regarding compromised containers.

- **Weight Poisoning:** Any modification to the physical bytes of the `TENSOR` payload inherently breaks the SHA-256 binding. The engine MUST treat this as a hostile poisoning attempt and immediately abort execution.
- **Certificate Revocation:** Engines SHOULD support Certificate Revocation List (CRL) or Online Certificate Status Protocol (OCSP) checks. If a developer's X.509 certificate is marked as revoked (e.g., due to a compromised private key), the engine MUST reject the container.
- **Tampered Lineage:** Modifications to the trailing `PROV` block will not invalidate the core tensor payload hash. However, strict-compliance runtimes MAY choose to cryptographically sign the `PROV` payload size and sentinel to prevent unauthorized append attacks.
